# Testing

```sh
tests/run_tests.sh                # static analysis + suite + coverage
tests/run_tests.sh --no-coverage  # just the first two
bats tests/                       # the suite alone
DT_VIS_AWK=mawk bats tests/       # pin the awk implementation
tools/coverage.sh [outdir]        # coverage alone
```

## What runs

| Stage | Tool | Scope |
|---|---|---|
| static | `shellcheck -x -S style` | `dt_vis.sh`, `tools/coverage.sh`, `tests/run_tests.sh`, `tests/helpers.bash` |
| static | `gawk --lint` | `lib/*.awk`, `tools/*.awk` |
| static | `python3 -m py_compile` | `tests/tools/dtb2fs.py` |
| dynamic | `bats` | 160 tests, re-run once per awk implementation found on the machine |
| coverage | `tools/coverage.sh` | statement coverage + annotated HTML |

Sanitizers (ASan/UBSan/TSan) do not apply — there is no compiled code in
this project. Their role here is played by `shellcheck` (the closest thing
bash has to a static analyser), `gawk --lint`, and the fault-injection tests
described below.

## Suite layout

| File | Covers |
|---|---|
| `00_cli.bats` | option parsing, validation, exit status, `DT_VIS_LIBDIR` |
| `10_lexer.bats` | comments, string literals, cpp directives — the cases a naive parser gets wrong |
| `20_structure.bats` | depth limiting, multi-root merge, `&label` and `&{/path}` fragments, `/delete-*` |
| `30_backends.bats` | dts / dtb / fdt back-ends, including cross-checking dtb against dts |
| `40_fdtval.bats` | unit tests for the FDT value type heuristic, byte sequence in → DTS token out |
| `50_robustness.bats` | malformed input, stray braces, 200-deep and 500-wide trees, CRLF, binary garbage |
| `60_corners.bats` | symlink invocation, engine defaults, fault injection, rarely-taken branches |
| `70_includes.bats` | `-i` include following: resolution order, search paths, auto-detection, duplicates, cycles, depth limit, `--origin` |

Fixtures:

* `tests/fixtures/sm8750-like.dtsi` — modelled on the real
  `arch/arm64/boot/dts/qcom/sm8750.dtsi`, trimmed but keeping every
  structural feature: multiple root blocks, `&label` and `&{/path}`
  fragments, labels, cpp macros and includes, both comment styles, byte
  strings, multi-line cell arrays, `/delete-node/`, `/delete-property/`,
  and a string containing `{`, `;` and `/*`.
* `tests/fixtures/board.dts` — small and `dtc`-compilable, so the same
  logical tree can be checked through all three back-ends.
* `tests/tools/dtb2fs.py` — expands a `.dtb` into the directory layout the
  kernel exposes at `/proc/device-tree`, so the FDT back-end is testable on
  a build machine with no board attached.
* `tests/fixtures/inc/` — an include graph with every case that matters: a
  C header that must be skipped, a quoted include, an angle include reached
  through `-I`, a diamond (the same file included twice), a two-file cycle,
  and fragments whose labels live in the includes.
* `tests/fixtures/ktree/` — a stub kernel tree (`scripts/dtc/include-prefixes`
  plus `arch/arm64/boot/dts/...`) so include auto-detection is tested without
  needing a real kernel checkout.

### Cross-validation

`30_backends.bats` asserts that the `.dts` and `.dtb` back-ends produce the
same tree shape for `board.dts`, and `40_fdtval.bats` pins the value
decoder against `dtc`'s own type-guessing rules. The `.dtb` fixture is
regenerated by `dtc` in `setup_file`, so the reference is `dtc` itself, not
a recorded string.

### Fault injection

Three tests deliberately break the environment rather than the input:

* an `od` on `PATH` that always fails, to reach the "cannot decode this
  property" path;
* a `PATH` containing everything except `dtc`, to reach the "you gave me a
  blob but have no decompiler" error;
* `setpriv --reuid=65534` to run as an unprivileged user, so the
  permission-denied branch is reachable on a root-only build machine.

## Coverage methodology, and what the number means

`kcov` — the usual answer for bash — was dropped from Ubuntu 24.04, and
`bashcov` needs a reachable rubygems mirror. So coverage is built from what
the two languages already provide.

**bash.** `tools/coverage.sh` re-runs the whole suite with `$DTVIS` pointed
at a shim that turns on `set -x` with

```sh
PS4='@${BASH_SOURCE}:${LINENO}@ '
```

and then *sources* the real script, so `$BASH_SOURCE` and `$LINENO` refer to
`dt_vis.sh` and not to the shim. The trace is parsed back into a set of
executed line numbers.

**awk.** The shim for `$DT_VIS_AWK` invokes `gawk --profile`, whose output
is a pretty-printed copy of the program with an execution count against
every statement it ran. Counts from all ~700 invocations are summed by line
index — legitimate because the pretty-printed listing is deterministic once
the count column, the `# N` branch annotations and indentation are
normalised (verified before relying on it).

**The honest caveat.** For gawk the *denominator* is exact: gawk knows which
lines are statements. For bash it is not — bash has no notion of an
"executable line", so `tools/cov_bash.awk` derives one heuristically,
excluding blank lines, comments, here-document bodies, function headers,
bare `case` pattern labels, and the structural keywords bash never traces
(`fi`, `done`, `esac`, `else`, `then`, `do`, `;;`, `{`, `}`). Backslash-
continued commands are treated as one unit, because bash attributes such a
command to exactly one of its lines and empirically not always the first.

So the bash figure is *statement coverage under a documented approximation
of the statement set*, not instrumented coverage. It is auditable: every
line's classification is in `coverage/bash.tsv`, and the annotated HTML
report colours each line, so a wrong classification is visible rather than
hidden inside a percentage.

There is also no **branch** coverage here — neither mechanism reports which
side of a condition was taken. 100% statement coverage means every line ran,
not that every path did.

## Reports

```
coverage/html/index.html      summary + links
coverage/html/*.html          per-file annotated listings
coverage/summary.txt          the table above
coverage/*.tsv                per-line: lineno, state (E/U/N), hits, text
coverage/bats.log             the instrumented run's output
```

Grep the TSVs for `\tU\t` to list uncovered lines.

## Adding a test

```bash
@test "short description of the behaviour" {
	f=$(mkdts <<-'EOF'
		/ { a { }; };
	EOF
	)
	run dtv -d 1 "$f"
	assert_status 0
	assert_has "-- a"
}
```

`dtv` runs `dt_vis.sh` with `-C never -a` so assertions are stable.

**Assert on `"-- a"`, not `"a"`.** The first line of the output is the input
file's name, and `mkdts` names files with a random `mktemp` suffix — a bare
`assert_has "a"` can pass because the *filename* contained an `a`. Anchoring
on the tree connector removes that whole class of false pass. (This was a
real bug in an earlier version of this suite.)
